# KubernetesPool Interactive Launcher - Incremental Changelog

- Added an opt-in interactive mode to the existing KubernetesPool external-SDK production runner without replacing Kubernetes lifecycle, scale-out, queue, admission, recovery, DAG, journal, or result-acceptance authorities.
- Added a three-client KubernetesPool orchestrator for the external .NET, TypeScript, and Python interactive-agent consumers.
- Added fail-closed live Kubernetes topology attestation bound to the exact generated pool identifier, Ready Pod membership, stable Service presence, runtime-instance-count annotation, and configured Runtime Pool image.
- Added an interactive launcher that pins local JWT claims to the existing Kubernetes matrix project, tenant, tenant group, and namespace while keeping signing material server-owned.
- Removed the historical non-secret Kubernetes OpenAI placeholder from interactive control-plane command-line settings so the server environment can supply the real provider credential through the existing KubernetesPool host-option projection.
- Preserved the external consumer credential firewall; OpenAI and JWT signing secrets are removed before external SDK processes are launched.
- Added provider-key redaction to retained kubectl diagnostics when Runtime Pool arguments expose the projected OpenAI setting.
- Preserved the bounded replay-readiness behavior already validated by the ProcessHostPool interactive scenario.
- Added structural verification and Kubernetes topology-attestation unit coverage.
- Historical Kubernetes matrix execution remains unchanged when interactive mode is not selected.

- Enabled the existing durable Child DAG composition feature gate on the interactive Kubernetes control plane and projected the same feature gate into RuntimeInstanceOnly children; this restores `IAiChildExecutionRelationStore` and the existing child continuation services for the interactive-agent pipeline without changing Kubernetes lifecycle or execution authority.
- Improved early-publication failure diagnostics so a consumer exit before scale-out is reported as a client/public-boundary failure instead of being masked as a Kubernetes topology-attestation timeout, and the runner prints retained control-plane log tails when no dedicated interactive client log exists.
